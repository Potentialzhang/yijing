# ADR-0002：历法与干支时间工具的规则边界（草案）

> 日期：2026-08-26  
> 状态：待内容负责人复核  
> 适用阶段：M2-B01～M2-B06

## 背景

M2 的时间工具必须同时处理公历、农历、二十四节气和干支。它们并不是同一套月份或换日规则；如果在没有规则版本和边界样例的情况下直接编写计算函数，用户会得到看似精确、实际无法追溯的结果。

香港天文台的历法资料明确区分农历与太阳位置，并说明二十四节气按太阳在黄道上的位置定义；其教育资料还说明，年干支换年存在约定差异，并以农历正月初一作为其年历的换年依据。参考资料：

- [香港天文台：今夕是何年？](https://www.hko.gov.hk/en/education/astronomy-and-time/time-service/00506-what-year-is-it-today.html)
- [香港天文台：二十四节气](https://www.hko.gov.hk/en/gts/time/24solarterms.htm)
- [香港天文台：2026 年年历索引](https://www.hko.gov.hk/en/gts/astron2026/almanac2026_index.htm)

## 提议决策

### 1. 输入必须带时区

所有计算输入使用：

```ts
interface CalendarInput {
  instant: string;       // ISO 8601，必须包含偏移或按 timeZone 解读
  timeZone: string;      // IANA，例如 Asia/Shanghai
  ruleVersion: string;   // 规则版本，不允许隐式采用最新规则
}
```

页面必须显示实际采用的时区和规则版本。默认使用浏览器当前 IANA 时区，用户可以改为明确的 IANA 时区；不把服务器时区当作用户时区。

### 2. 把“日历日期”和“干支层”分开

输出分层保存，不能用一个 `month` 或 `year` 字段混合不同体系：

- 公历日期：年、月、日；
- 农历日期：农历年、月、日、闰月标记；
- 二十四节气：节气名称、事件时刻、采用时区、精度说明；
- 干支年/月/日/时：每一层都带 `basis`、`ruleVersion` 和可解释的边界说明。

### 3. 以下边界必须显式选择，不能静默猜测

| 边界 | 候选规则 | 首版状态 |
| --- | --- | --- |
| 干支年换年 | 农历正月初一 / 立春 | 待内容负责人确认 |
| 干支月 | 农历月 / 节气月（节） | 待内容负责人确认 |
| 干支日换日 | 本地民用午夜 / 子初 / 真太阳时 | 待内容负责人确认 |
| 子时跨日 | 23:00 起算 / 00:00 起算及其对应日柱 | 待权威样例确认 |
| 地方时 | 标准时 / 真太阳时修正 | 首版默认不使用，待确认 |
| 二十四节气精度 | 事件时刻 / 日期级展示 | 由数据来源与版本决定 |

在这些选项未确认前，应用只提供 M2-A 的静态学习内容，不展示自动干支排盘结果。

## 规则版本与输出约束

- 每次规则变更新增 `ruleVersion` 和 ADR，不覆盖历史记录；
- 规则集必须登记 `sourceIds` 与 `authoritativeSampleIds`；在边界完整、来源和样例均经复核前保持 `draft`，不能标记为 `accepted`；
- 节气结果保存事件时刻、来源、时区和精度，不能只保存一个日期字符串；
- 计算页面必须展示“输入时间 → 时区转换 → 边界判断 → 输出”的步骤；
- 无法确定或缺少来源时显示“待确认”，不得用 AI 或默认值填补；
- 该工具只用于学习与核对，不做吉凶、风水或现实决策建议。

## 权威样例验收清单

实现 M2-B02～B06 前，内容负责人需要提供带来源定位的样例集，至少覆盖：

1. 年末、年初以及农历正月初一/立春相近日期；
2. 节气交接前后各一组，包含事件时刻和时区；
3. 农历月末、闰月和跨公历月日期；
4. 23:00～00:00 的子时跨日样例；
5. 至少两个 IANA 时区的同一瞬间对照；
6. 每个样例的规则版本、原始来源、引用定位和期望输出。

样例未通过双人复核前，ADR 保持“待内容负责人复核”，不得将计算模块标记为 DONE。

## 未采用方案

- 不直接复制未经授权的第三方万年历数据；
- 不把农历月份、节气月份和公历月份混成一个下拉选项；
- 不以固定日期近似二十四节气；
- 不把某一流派的换日习惯包装成唯一正确答案；
- 不在没有真太阳时、磁偏角和误差说明时输出“精确方位”。
